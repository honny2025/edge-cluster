## 二、真机暴露出的硬约束（这条必须先知道）

平台显示 `CPU —`，**不是配错了**。我查了库里的 121 条真机采样：

| 指标 | 空值率 | 原因 |
|---|---|---|
| `cpu_usage` | **121/121 全空** | Android 8+ SELinux 禁止普通 App 读 `/proc/stat` |
| `load_avg` | 121/121 全空 | `/proc/loadavg` 同样被封 |
| `net_rx_bytes` / `net_tx_bytes` | 121/121 全空 | `/proc/net/dev` 同样被封 |
| `gpu_usage` | 82/121 空 | 🟡 **部分可读**（devfreq），值约 3.3% |
| 内存 / 存储 / 温度 / 电池 / CPU 频率 | **0/121 空** | ✅ 完全正常 |

这不是本项目的 bug，是系统限制（`termux-app#299`、`psutil#2195` 有记录）。
项目「拿不到就留空、不造假」的原则在这里**表现为正确的 —**，但它意味着：

> **§4 要求的「CPU / GPU / NPU 使用率」在免 root 的 Android 上拿不到真值。**

三条出路（我建议 1+3 组合）：

| 方案 | 代价 | 效果 |
|---|---|---|
| 1. 运行时自动探测降级链：`/proc/stat` → PSI → cpufreq 频率占比 → 进程自身 CPU，**每个值都标注来源，代理指标不冒充使用率** | 小 | 诚实地给出"能给的" |
| 2. 用 Shizuku / ADB 授权读系统接口 | 中 | 拿到真 CPU%，但需用户动手激活 |
| 3. 前台把 `—` 变成**有解释的状态**（"Android 限制，已用频率占比替代"） | 小 | 用户不再以为是故障 |

> ⚠️ 平台侧改动（鉴权、节点 IP）**需要重启平台才生效**。现在对运行中的平台跑 `m3_check.py`

## 七、顺手记下的五个坑

1. **Acceptance 脚本必须绕开系统代理**：本机设了 `HTTP_PROXY`，访问 `127.0.0.1` 会被代理拦成 **502**，
   看起来像"平台挂了"。`m3_check.py` 已用 `ProxyHandler({})` 处理（Agent 侧本来就有同款处理）。
2. **节点上报的 IP 可能不是能访问的那个**：`honor-x70` 上报的是 `10.95.115.77`（校园网侧），
   而电脑实际要访问它得走热点侧 `10.86.33.31`。`local_ip()` 用 `connect(("8.8.8.8",80))` 取源地址，
   在"双网卡 + 开热点"场景下会选错网卡 —— **§6/§7 登记服务 Endpoint 之前必须先修这个**
   （本轮已修，见第六节），否则平台给出的调用地址是错的。
3. **WS 路由不在 `/api/v1` 前缀下**：真实路径是 `/ws/agent` 和 `/ws/dashboard`，写验收脚本时
   按 REST 习惯拼 `/api/v1/ws` 会得到 403（Starlette 在 `accept()` 前 `close()` 就回 403，
   看起来像 token 错，其实是路径错）。
4. **REST 鉴权头是 `X-Auth-Token`，不是 `X-Token`**：`X-Token` 一律 401。
