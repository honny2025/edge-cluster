## 摘要：我给的建议按优先级分四档

| 档 | 建议 | 为什么急 |

| **必须在 M3 动手前定** | O1 运行时适配层、O6「当前任务」语义 | 这两个决定 M3 的数据库表结构，改晚了要迁移数据 |

## 第一部分：必须在 M3（模型下发）动手前决定

### O1. 先定义"运行时适配层"，否则 M3 会做成一堆 if-else [判断]

**问题**

原需求 §3 说"模型服务配置驱动，禁止硬编码任何模型"——这个原则是对的。
但需求没有回答一个更靠前的问题：**谁来真正执行推理？**

手机 Termux 环境下，能选的推理途径其实很有限，且各有硬约束：

| 途径 | 在 Termux 下的现实 | 约束 |
|---|---|---|
| `llama.cpp`（GGUF） | 相对最可行，可编译或找预编译二进制，纯 CPU 推理 | 需要自己编译或解决二进制分发；ARM64 优化参数要调 |
| `onnxruntime` | pip 有包，能装 | **NNAPI 加速基本不可用**——需要 native/NDK 环境，Python 包拿不到 |
| `transformers` / `torch` | 装得动但很重，ARM 下性能差 | 内存开销大，Termux 编译轮子常失败 |
| `PaddleOCR` / `ultralytics` | opencv 依赖在 Termux 上安装是硬仗 | 容易卡在编译环节 |
| 自己写的小服务 | 最可控 | 需要用户自己开发 |

**如果不先抽象，M3 会变成什么**

平台下发一个模型 → Agent 要判断"这个模型该用什么命令启动" →
于是代码里出现 `if model.format == "gguf": ... elif ...`。
**这就违背了 §3 自己定的"禁止硬编码"原则。** 每加一个模型类型就改一次 Agent 代码。

**建议**

定义 `runtime`（运行时）适配层，把"怎么启动"从 Agent 代码里剥离出来：

```jsonc
// service_defs/qwen2.5-3b-q4.json —— 一个服务定义示例（M3/M4 使用）
{
  "service_key": "qwen2.5-3b-q4",
  "display_name": "Qwen2.5-3B-Q4 对话服务",
  "runtime": "llamacpp",              // ★ 关键字段：交给哪个适配器
  "model_file": "qwen2.5-3b-instruct-q4_k_m.gguf",
  "api_kind": "openai",               // openai / vision / ocr / custom
  "default_port": 8080,
  "resource": {
    "mem_required_mb": 2800           // ★ 供 O4 的资源准入使用
  },
  "run": {
    // 启动参数模板。{port} {model_path} {ctx} 等占位符由适配器填充
    "args": ["-m", "{model_path}", "-c", "{ctx}", "--host", "0.0.0.0", "--port", "{port}"]
  },
  "params_schema": [                  // 平台 UI 据此动态生成参数表单
    { "key": "ctx", "label": "上下文长度", "type": "int", "default": 4096, "min": 512, "max": 32768 }
  ],
  "health": { "path": "/health", "timeout_sec": 120 }
}
```

**至少实现三种 runtime**：

| runtime | 做什么 | 价值 |
|---|---|---|
| `llamacpp` | 按模板拼参数、拉起 `llama-server`、探活 | 覆盖 LLM 主场景 |
| `onnxruntime` | 拉起一个通用 ONNX 推理 wrapper | 覆盖视觉/OCR 模型 |
| **`custom-cmd`** | **用户直接写启动命令，平台只管进程** | ★ **万能兜底** |

**`custom-cmd` 是这条建议的关键。** 有了它：
- 平台不需要预先支持任何推理引擎
- 用户想跑什么奇怪的东西都能接上
- 新引擎出现时，用户自己就能用，不用等平台更新

这才是"配置驱动"的完整形态——**平台负责"管进程、管文件、管接口"，不负责"懂模型"**。

**成本**：中等。要在 M3 设计数据库时就把 `runtime` / `resource` / `params_schema` 这些字段留出来。

### O6. 「当前任务」字段语义太模糊，一定会变成没人填的字段 [判断]

**问题**

原需求 §4 要求设备管理页面展示"**当前任务**"。但这个词有三种完全不同的含义：

1. 正在下载/安装的模型？（部署任务）
2. 正在运行的模型服务列表？（运行态）
3. 最近一次推理请求？（业务态）

**如果不拆开**，结果通常是：实现时随便选一个填了，展示出来又不完整；或者干脆没人填，长期空着。

**建议**：拆成三个语义明确的字段

| 字段 | 含义 | 数据来源 |
|---|---|---|
| `deploying` | 正在进行的部署任务（含模型名、阶段、进度%） | M3 |
| `running_services` | 运行中的服务清单（含端口、状态） | M4 |
| `last_task` | 最近完成的任务及结果（成功/失败、耗时） | M3/M4 |

**收益**：前端可以明确显示"正在下发 Qwen2.5-3B：67%"，而不是一个含糊的"任务中"。

**成本**：低。只是字段设计的取舍，但要在建表前定——**M3 的 `deployments` 表就要承载这个语义**。

## 第二部分：必须在 M4（服务管理）动手前决定

### O2. 请求统计必须在数据路径上，Gateway 不能"以后再说" [判断 + 部分实测]

**问题**

原需求存在一处**内部矛盾**：

- §8 要求首页大屏展示："**模型服务请求量、吞吐量、延迟**"
- §7 却说："**后续**可增加统一 API Gateway，由平台自动把请求调度到不同手机节点"

**如果 MVP 不做网关**（请求直连手机上的服务），那么：
- 请求流量**根本不经过平台**
- 平台无从知道发了多少请求、多快、多慢
- 想拿到这三个指标，只能**在每个推理服务内部埋点**

而埋点这事对 `llama-server` 这种现成服务**做不到**——你没法改它的源码。

**结论：统计能力必须在数据路径上。事后再补，等于把数据路径推倒重来。**

**建议**：M4 就把网关做进去，但做成**可选的双路径**，两种模式并存：

| 模式 | 请求路径 | 优点 | 缺点 |
|---|---|---|---|
| **直连模式** | 客户端 → 手机服务 | 低延迟、调试方便、平台无关 | **无统计** |
| **网关模式** | 客户端 → 平台 → 手机服务 | **有完整统计**、可鉴权、可调度 | 多一跳、平台成为带宽瓶颈 |

**MVP 阶段网关只需做最简三件事**：
1. **转发**（HTTP 反代到目标节点端口）
2. **计时**（记录请求耗时，算 P50/P95）
3. **计数**（QPS、总量、token 数若响应体里有）

**不需要**一步到位做负载均衡、健康路由、优先级队列——那些是网关模式的第二步。

**额外收益**：网关模式是 §7"自动把请求调度到不同手机节点"的**唯一实现路径**。
两者是同一件事，不是两件事。先做最简网关，调度逻辑后加，成本远低于事后补统计。

**成本**：中等（一个反向代理 + 计数中间件），但**架构位置必须现在定**。

### O4. 不做资源准入，"一机多服务"就是空头承诺 [判断]

**问题**

原需求 §6 要求"**一个手机允许部署和管理多个模型服务**"。

现实是：手机内存 8~12GB，一个 7B-Q4 模型加载后吃 4~5GB。
**启动第二个大模型 → OOM → Android 的 LMK（低内存杀手）杀掉进程，
甚至可能把 Termux 本身杀掉**，导致节点失联。

用户的体感会是："说好支持一机多服务，我一启动第二个就崩了。"

**建议**：引入**节点级资源准入**，把"能不能启动"的判断前置。

```
准入条件：
  已运行服务占用 + 新服务预估需求 ≤ 节点可用内存 × 安全系数(0.8)

不满足 → 拒绝启动，并明确告知原因：
  "内存不足：已用 5.2GB / 可用 7.8GB，本服务需要 2.9GB，
   请先停止 [xxx] 服务，或改用更小的量化版本。"
```

配合两个机制：

| 机制 | 作用 |
|---|---|
| `mem_required_mb`（服务定义里填） | 提供准入计算依据。**人工预估即可**，宁可高估 |
| **互斥组**（`exclusive_group`） | 同组服务只能一个 running（如两个大模型互斥），不同组可共存（大模型 + 小 OCR 可以） |

**反面案例**（如果不做）：用户点了启动，界面转圈，然后服务变成 `error`，
日志里只有一句 `OOM killed`。用户不知道发生了什么，也不知道该怎么办。

**成本**：低-中。准入逻辑本身简单，难点是让人去填 `mem_required_mb`（可以给个默认估算公式兜底）。

## 第三部分：建议尽早做（成本低，收益随规模显现）

### O5. 下发队列与带宽治理（原需求完全没提） [判断]

**问题**

原需求 §5 说"支持批量部署"。但没考虑**批量下发的物理约束**：

把同一个 4GB 模型同时发给 5 台手机，意味着**同时在局域网上跑 20GB 流量**。

后果有两个：
1. **打满出口带宽**。心跳虽然走 WS（独立于 HTTP），但带宽饱和会延迟**所有**数据包，
   包括心跳。可能导致**多台节点集体误判离线**——系统自己把自己搞崩了。
2. **下发大面积失败**。手机存储写入速度有限，并发下载容易超时。

**建议**（五条，每条都对应一个真实会踩的坑）：

| # | 措施 | 防的是什么坑 |
|---|---|---|
| 1 | **下发队列 + 并发上限**（可配，默认 2） | 带宽打满导致集体误判离线 |
| 2 | **下发前磁盘空间预检** | "下到 99% 才失败"最伤用户 |
| 3 | **断点续传的一致性校验**：续传请求带 `ETag`/`Last-Modified`，与首次不一致则整文件重下 | 文件在断点期间被换了版本，续传出来的文件是**两个版本的拼接**，sha256 对不上但字节数对得上 |
| 4 | **完成判定 = 落盘后 sha256 校验通过**，不是"字节数够了" | 静默的数据损坏 |
| 5 | **下发期间临时放宽该节点的离线判定**，或标记为"忙"不参与常规告警 | 手机忙着写盘导致心跳延迟，被判离线 |

第 3 条特别值得一提：**字节数正确 ≠ 文件正确**。
如果续传时服务端的文件已经换成了新版本，你拿到的会是"前半段旧版 + 后半段新版"，
长度对得上、sha256 对不上。只有校验能发现。

**成本**：中。但这些都是"不做就会在真机规模上去后爆出来"的问题，
且**在下发模块里实现，比事后加要省事**。

### O9. 离线判定建议用「双阈值」，比单阈值更符合需求本意 [部分实测]

**实测事实**

任务书 §5 里程碑 1 要求"kill 掉 Agent → **15s 内**标记 offline"，
但 §5 里程碑 5 又要求"**心跳抖动容错、状态机防抖**"。

我们 M1 的实现是 `离线阈值 15s` + `连续 3 次巡检确认（5s/次）`，
**实测离线耗时约 20~25s**（`m1_check` + 手工 kill 实测 T+20s 变 offline）。

**这两条要求本身有张力**，我当时的处理是：优先保证防抖（不误报），
并把 `offline_confirm_times` 做成配置项（改成 `1` 即严格 15s），取舍写进了 README。
**没有擅自改数字**。

**建议：用双阈值替代单阈值，两条要求可以同时满足。**

| 阶段 | 触发条件 | 界面表现 | 是否告警 |
|---|---|---|---|
| `soft_offline`（疑似离线） | 15s 无心跳 | 黄灯 + "疑似离线" | **不告警** |
| `hard_offline`（确认离线） | 30s 无心跳 | 红灯 + "离线" | **告警** |

**为什么这比单阈值好**：
- "15s 内可见状态变化" ✅ 满足（黄灯）
- "不误报" ✅ 满足（不告警、不排除出汇总）
- 网络抖一下 → 黄灯闪一下又恢复，用户无感
- 真挂了 → 15s 黄灯、30s 红灯告警，反应足够快

**成本**：低。状态机加一个中间态，前端加一种显示样式。
但要注意：**这个决策会影响前端状态显示逻辑，越早定越好改。**

## 第四部分：可以延后（但要在对应阶段记着）

### O3. 「总算力」是个伪指标，建议拆成"估计值"和"实测值" [判断]

**问题**

原需求 §8 要求大屏展示"**总算力**与设备资源使用情况"。

问题在于：**手机 SoC 的算力没有统一可比口径。**

- **NPU 的 TOPS**：厂商口径不一（有的标 INT8、有的标 INT4，有的带稀疏加速，有的标峰值有的标持续），
  **不同代际、不同厂商之间累加毫无意义**。
- **CPU 核数 / 主频累加**：更假——大核小核混在一起累加，跟真实算力没关系。
- 一个看起来专业的"总算力 45 TOPS"数字，**没有任何决策价值**，而且会误导人。

**建议**：拆成三个**口径明确**的指标，并且**明确标注哪些是估计**：

| 指标 | 口径 | 性质 |
|---|---|---|
| 平均资源使用率 | 在线节点的 CPU/内存实测均值 | **实测** |
| 节点算力档位 | 旗舰 / 次旗舰 / 中端（**人工标注**） | **估计**，仅用于调度偏好 |
| **实际吞吐** | tokens/s 累加、图片/秒 | **实测**（依赖 O2 的网关） |

**关键原则**：前两个是估计、第三个是实测，**在界面上必须分开呈现**，
不能揉成一个"总算力 xx"。

**为什么第三个才是真的**：只有"每秒钟实际产出了多少 token / 多少张图"是真实的算力体现。
它需要网关才能采集，所以**这条依赖 O2**。

**成本**：低（前端展示口径调整），但**需要你先认同"不做假指标"这个原则**。
考虑到这个项目在别处（指标留空、离线不下发旧值）已经贯彻了"不造假"，
这里保持一致比较自然。

### O7. 安全边界要写进文档，别让默认配置上生产 [实测 + 判断]

**实测事实**

当前实现（按原需求 §7 约定）：
- 共享 token 鉴权，**明文 HTTP 传输**
- 无多用户、无权限、无 HTTPS
- 无 token 访问会返回 **HTTP 401**（这点已实测）

**风险（判断）**

局域网内任何设备只要抓包，就能拿到 token，进而：
- 查看所有设备和指标（信息泄露）
- 伪造节点注册（数据污染）
- **M4 之后还能远程启动手机上的服务、下发任意文件到手机**（执行能力）

**我认为这不只是"没做权限"，而是"给了他人执行能力"**——性质比单纯的信息泄露严重。

**建议（按成本排序）**

| 措施 | 成本 | 效果 |
|---|---|---|
| **启动时检测默认 token 并打警告** | 极低（几行代码） | 至少避免"用公开默认口令" |
| 文档明确写"仅限可信局域网" | 零 | ✅ **已在操作说明书 §9.3 落实** |
| 网关模式下每服务单独签发 API key | 中 | 限制单点泄露的范围 |
| 上公网则必须 HTTPS + 设备证书 | 高 | 真正解决（当前明确不做） |

**我不建议现在停下来做安全加固**——按原需求 §7，这不在 MVP 范围内。
但**强烈建议加上第一条**（默认 token 警告），成本几乎为零。

### O10. 指标存储建议提前定「分层保留」策略 [判断 + 部分实测]

**实测事实**

当前配置：
- 保留 **7 天**原始采样（`metric_retention_days = 7`）
- 同节点两次入库最小间隔 **2s**（`metric_min_interval`）
- 每天自动清理一次（实现在心跳巡检里，已确认可用）

按每 5s 一个采样算：**单节点每天约 1.7 万行**。
10 节点 × 7 天 ≈ **120 万行**——SQLite 扛得住。

**但有个实际问题（判断）**：查"近 24 小时曲线"时要返回约 1.7 万个点，
前端渲染会卡，传输也浪费。现在的实现是靠 `limit` 参数截断，
**等于丢掉了时间维度的完整性**（截断后曲线只覆盖部分时段）。

**建议：分层保留（rollup）**

| 层级 | 粒度 | 保留 | 用途 |
|---|---|---|---|
| 原始 | 5s | 2 天 | 精细排查 |
| 分钟聚合 | 1 分钟 | 30 天 | 日常趋势（24h 曲线用这层） |
| 小时聚合 | 1 小时 | 1 年 | 长期容量规划 |

**收益**：
- 24h 曲线只需 1440 个点，渲染流畅
- 长期趋势可查（现在 7 天前的数据是直接删掉的）
- 数据库不会无限膨胀

**成本**：中（要加聚合表 + 聚合任务）。**但拖得越久，历史数据越难回填**——
已删除的原始数据是无法重建聚合的。

**时机建议**：M5 或数据量上来之前做，别等到有人想查"上个月的负载趋势"时才发现没有。

### O8. 建议把「P2P 优先」反转为「中继保底 + P2P 优化」 [判断]

**问题**

原需求 §3 写的优先级是：
> **P2P 跨公网连接优先**，必要时增加服务器中继

**我的判断：这个顺序反了。**

理由：

1. **国内移动网络大量处于 CGNAT 之后**，UDP 打洞成功率不稳定。
   同一套代码，A 运营商能连、B 运营商连不上，且**用户无法判断为什么**。
2. **Termux 环境下做打洞受限**——需要操作 socket、维持 NAT 映射，
   在 Android 的后台限制下更难保证长期有效。
3. **对"无人值守集群"来说，不确定性比延迟更致命**。
   P2P 优先的体验是"有时能连有时不能"，中继优先的体验是"一定能连，就是慢一点"。

**建议的优先级**：

```
中继保底（100% 可用） + P2P 优化路径（命中则切直连降延迟）
```

**工作量上的好处**：中继只需一个 WebSocket/HTTP 转发服务，实现简单、行为确定；
P2P 作为**优化**而非**前提**，可以做在第二阶段，成功一个算一个，
失败就自动回落中继，不影响可用性。

**架构上已经兼容**：M1 已经把连接层抽象成 `core/transport.py` 的 `Transport` 基类，
换实现即可，业务层无感知。这就是当初做抽象的价值。

**成本**：属于远期工作，但**优先级定义现在改掉，比实现完再改要省事**。

## 附：我认为原需求写得好的地方（保持）

评审不能只挑毛病。以下几点我认为是这份需求里**明显优于常见写法**的，建议坚持：

| 点 | 为什么好 |
|---|---|
| **§4 明确要求"区分没有上报 / 节点离线 / 服务停止 / 服务异常"四态** | 大量监控系统把这几件事混成一个"异常"，导致排查方向全错。这个要求很专业 |
| **§4 "指标拿不到要留空，不造假"** | 这是整个项目最有价值的一条原则。已贯彻到 M2（曲线断点、汇总 null、离线不下发旧值） |
| **§3 "禁止硬编码任何模型"** | 避免了把平台做成"只支持某几个模型"的死板工具 |
| **§6 "只做抽象不含实现"** | 架构预留而非过度设计，分寸很好 |
| **§7 "明确不做"清单** | 明确划出边界，比"什么都要"的需求健康得多 |
| **§8 "每个里程碑可运行 + README 更新 + 可复现验收步骤"** | 强制了"能跑起来"这个底线 |
| **§8 "面向长期无人值守写错误处理，单点错误不允许拖垮进程"** | 符合边缘场景的真实诉求 |

我认为 **O1（运行时适配层）和 O2（网关进数据路径）** 两条建议，
本质上是在补全"§3 禁止硬编码"和"§8 请求统计"这两条好原则**落地时缺的那一环**——
原原则是对的，只是没说清具体怎么落。
