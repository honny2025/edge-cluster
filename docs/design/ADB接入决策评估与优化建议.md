## 一、ADB 到底要不要加

### 1.1 先拆开：你说的「ADB」其实是两件完全不同的事

| 用法 | 干什么 | 建议 |
|---|---|---|
| **ADB 作为装机工具**（一次性） | 激活 Shizuku、`adb push` 拷文件、真机排障 | ✅ **推荐**。你项目里已经在这么用了（`deployment.md:167`、`user-manual.md:566`） |
| **ADB 作为运行时通道**（常连） | 平台/PC 持续 `adb shell` 连着手机读指标 | ❌ **反对**。见 1.2 |

这两件事被混为一谈，是分歧的根源。

### 1.2 三条提权路径对比 [判断 + 部分实测]

| | ADB 常连 | **Shizuku** | root (Magisk) |
|---|---|---|---|
| 连接方向 | **PC → 手机（入站）** | 手机**本地** IPC | 手机本地 |
| 是否打破「平台不主动连手机」 | ✅ **打破** | 否 | 否 |
| 手机重启后 | 无线调试失效，**需重新配对** | 非 root 方式**需重新 adb 激活一次** | 开机自启 |
| 暴露面 | 局域网开放 5555，**无鉴权**（历史上被蠕虫扫过） | 手机上一个高权限本地服务 | 全机 |
| 平台换电脑 / 异地管理 | **彻底失效** | 不受影响 | 不受影响 |
| 拿到什么权限 | shell（uid 2000） | shell（uid 2000）或 root | root |

**关键差异不是"能不能读到"，而是"谁来发起连接"。**
Shizuku 是**手机内部的权限提升**，网络拓扑一点没变 —— Agent 依然主动拨出 WebSocket，平台依然不主动连手机。ADB 常连则是把拓扑反过来了。

### 1.3 收益边界 —— 这一节比 1.2 更重要

`需求覆盖评估与实施计划.md:47-51` 实测 121/121 样本的空值分布，逐项看提权后能救多少：

| 指标 | 当前 | 提权后 | 说明 |
|---|---|---|---|
| `cpu_usage` | 121/121 空 | ✅ **能救** | `/proc/stat` 在 shell uid 下可读 |
| `load_avg` | 121/121 空 | ✅ **能救** | `/proc/loadavg` 同上 |
| `net_rx_bytes` / `net_tx_bytes` | 121/121 空 | ✅ **能救** | `/proc/net/dev` 或 `/sys/class/net/*/statistics/` |
| `gpu_usage` | 82/121 空（约 3.3%） | 🟡 **可能多读几个节点** | 依赖机型 sysfs，非通用 |
| **NPU** | 无数据 | ❌ **救不了** | NPU 使用率**根本没暴露给用户态**，各家（麒麟/高通/天玑）私有，root 也多半拿不到 |

> **如果你上 ADB 的动力是"让首页不再全是 —"，它只能填掉 4 项中的 3 项。NPU 那一格大概率永远是 —。**
> 这不是我的悲观，是 `做不了功能解决方案.md:26` 自己写的："NPU 使用率根本没暴露给用户态"。

**这个账要先算清楚再动手** —— 否则做完会觉得白干。

### 1.4 如果决定做：我建议的形态

在 `agent_metrics.py` 现有降级链之上，加一个**可选的特权后端**，不是替换：

```
采集顺序：
  1. rish（Shizuku，shell uid 2000）  ← 新增
  2. tsu / sudo（root）              ← 新增
  3. 现有降级链（/proc 直读 → PSI → cpufreq → 自身占用）
  4. None（留空，前端显示「—」）
```

五条硬要求：

| # | 要求 | 为什么 |
|---|---|---|
| 1 | **必须可选、可关闭**，提权不可用就静默回退 | 不能因为 Shizuku 没装就让 Agent 崩或指标全丢 |
| 2 | **降频采集**：特权指标 30s 一次，不跟 5s 心跳走 | 每次 `rish -c` 要 fork 进程 + Binder IPC，5s 一次对手机是实打实的电量和 CPU 开销 [判断] |
| 3 | **沿用现有 `extra` 来源标注**：`cpu_source: "proc_stat_via_rish"` | 项目已有这个机制，前端不用改就能显示"来源：提权读取" |
| 4 | **失败只降级不报错** | 符合项目"拿不到留空、不造假"的硬纪律 |
| 5 | **验收脚本先写**：`agent_metrics_check.py` 加一个合成 `rish` 的用例 | 你已有 20/20 的合成环境验收，加一条成本很低 |

配套（成本极小，建议一并做）：
- `probe_metrics.sh` 加一段：`command -v rish` 存在时，用它重跑 `/proc/stat`、`/proc/loadavg`、`/proc/net/dev`，输出对比。**用户跑一次脚本就能知道"提权到底能多拿到什么"**，不用猜。
- `真机接入-Termux端.md` 增加一节：Shizuku 安装 + `adb shell` 一次性激活 + 重启后如何重新激活。

### 1.5 怎么回应「ADB 是手机接入的总协议」

三句话，都有抓手：

1. **ADB 不是"读状态的协议"，是远程 shell 通道。** 真正提供状态的是 `dumpsys` / `getprop` / `/proc`。证据：你 `agent_metrics.py:63-69` 就在调 `getprop ro.product.model` —— **这条命令 Termux 里现在就能跑，不需要 ADB**。
2. **它强的不是协议，是 uid。** ADB 能读到全量状态，是因为它以 shell（uid 2000）执行。同一个 `cat /proc/stat`，换 uid 就有不同结果。**Shizuku 给你同样的 uid 2000，但不改变网络拓扑。**
3. **没有"总协议"这回事。** 手机状态读取是分层的：内核 `/proc` / `/sys`（Linux 通用，与 ADB 无关）→ Android Framework API → termux-api → ADB（外部调试通道）。它们不是同一个东西的替代品。

## 二、其他可优化的地方

按我认为的性价比排序。P0 = 影响"这东西能不能真的用起来"。

### P0-1 真机闭环还没跑通 —— 当前**最大**风险 [实测]

- **证据**：`实现情况报告.md:11` 的端到端验证是「**模拟 Agent（PC 上 `--simulate`）+ 本地 mock HTTP 服务**」；`:53` 明确写「未在真机上重跑」。
- **含义**：M3（模型下发）、M4（服务管理）、网关这三块**目前只有模拟环境的证据**。真机上可能暴露：Termux 下 `Popen` 权限、端口绑定、路径、内存限制、进程被杀 —— 这些模拟环境全都测不出来。
- **建议**：先做一次**真机最小闭环**，再谈别的优化：
  1. 上传一个 **10MB** 的假模型 → 下发到 `honor-x70` → 看真实进度与 sha256
  2. 起一个 mock OpenAI 服务 → 网关 `/invoke` 调通
  3. `kill` 掉进程 → 看是否自动拉起、状态是否 `error` 再回 `running`
- **成本**：一次真机操作（半小时到两小时，看踩坑数）
- **为什么排第一**：这件事没跑通之前，后面所有优化都是"在没验证的地基上装修"。

### P0-2 保活状态应该变成可观测指标 [判断]

- **现象**：Termux 后台被杀是这个方案的第一杀手，但**目前没有任何可观测性** —— 节点掉线时，你分不清是"网络断了"还是"进程被系统杀了"。
- **建议**：Agent 每次心跳多带几个自描述字段，平台在节点详情展示：
  - `agent_uptime_sec`（进程活了多久，比"在线时长"更能看出是否被杀重启）
  - `restart_count`（本次开机后 Agent 被重启过几次）
  - `battery_optimization_exempt`（是否在电池优化白名单，可用 `termux-api` 或 `dumpsys` 判）
  - `wake_lock_held`（是否持有 wake-lock）
- **价值**：把"手机怎么又掉了"从玄学变成可排查的数据。这条 O1~O10 里没有，我认为是被漏掉的一条。
- **成本**：低（几个字段 + 前端一行展示）

### P1-1 网关 10 秒硬超时 —— LLM 场景必炸 [实测]

- **证据**：`server/app/api/routes_gateway.py:68` → `httpx.AsyncClient(timeout=10.0)`，**硬编码**。
- **问题**：网关模式要转发的正是 LLM 推理请求。手机上跑 3B~7B 模型，生成几十个 token 轻松超过 10 秒。**结果是正常请求被平台主动掐断**，前端表现为"服务时好时坏"。
- **建议**：超时改成**按服务可配**（`service_defs` 里加 `timeout_sec`，默认 120s），至少先提到一个安全值。
- **成本**：极低（一行 + 一个配置项）
