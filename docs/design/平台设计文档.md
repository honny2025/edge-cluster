# 平台设计文档

> 手机边缘计算集群管理平台 · edge-cluster
>
> 版本：v1.0　日期：2026-10-05
>
> 本文只保留设计说明，不包含代码和配置示例。

## 1. 平台定位与边界

平台将局域网或公网中的 Android 手机统一抽象为边缘计算节点，通过 Web 控制台完成节点纳管、监控、模型分发、服务托管和统一调用。

平台负责：节点注册与在线管理、指标采集、模型分发与校验、Runtime 生命周期、任务队列、网关转发和审计记录。

平台不负责：QNN 推理执行、模型转换与量化、算子调度、硬件加速细节。

设计原则：

- ADB 只用于救援，Agent 负责日常运行。
- Agent 主动连接平台，平台不主动连接手机。
- 平台负责生命周期，不实现推理。
- 传输层保持抽象，后续可接入 P2P 和 Relay。

## 2. 总体架构

平台由三部分组成：

| 部分 | 主要职责 |
|---|---|
| 平台服务端 | REST API、WebSocket、节点注册、任务调度、数据存储、网关转发 |
| Web 控制台 | 节点、模型、部署、服务和集群指标的可视化管理 |
| 手机 Agent | 注册、心跳、指标采集、模型下载、Runtime 启停和日志上报 |

主要通信方式：

| 通信 | 用途 |
|---|---|
| Agent → 平台 WebSocket | 注册、心跳、指标、指令回执 |
| 平台 → Agent WebSocket | 部署、启停、日志等控制指令 |
| Agent → 平台 HTTP | 模型下载，支持断点续传 |
| UDP 广播 | 局域网自动发现 |
| 平台 → Runtime HTTP | 服务探活和请求转发 |
| 浏览器 → 平台 HTTP/WebSocket | 控制台数据和实时事件 |

平台、Agent、Runtime 的端口均可配置。设备身份使用稳定的 Device ID，不能使用 IP 作为身份。

## 3. 后端设计

后端采用“接口层—业务服务层—数据层”结构。

- **接口层**：提供系统、节点、模型、部署、服务、网关 REST 接口，以及 Agent 和控制台 WebSocket。
- **节点服务**：处理注册、心跳、在线状态、IP 更新、节点删除和重启归零。
- **指标服务**：保存 CPU、内存、存储、温度、电池等指标，提供历史查询和集群聚合。
- **发现服务**：监听 UDP 广播并返回平台地址。
- **部署队列**：限制并发，跟踪任务进度、校验结果和失败原因。
- **服务管理**：下发 Runtime 启停、重启、探活和日志查询指令。
- **网关服务**：将请求转发到节点上的 Runtime，并记录次数和耗时。
- **连接层**：当前使用本地 WebSocket 传输，预留 P2P 和 Relay 实现。

## 4. 前端设计

控制台包含以下页面：

- **总览**：节点数量、在线状态、资源使用和告警。
- **节点管理**：节点列表、详情、历史指标和服务列表。
- **模型管理**：模型上传、版本、大小、校验值和删除。
- **部署管理**：选择模型和节点，查看进度、结果和失败原因。
- **服务管理**：创建 Runtime，执行启动、停止、重启、探活和日志查看。
- **服务调用**：通过平台网关访问节点 Runtime。

前端通过统一 API 客户端访问服务端，通过 WebSocket 接收节点状态、部署进度和发现事件。

## 5. 设备端 Agent

Agent 运行在 Android/Termux 环境，免 Root 工作，真机和模拟器使用同一套逻辑。

主要职责：

- 自动生成或读取 Device ID，并向平台注册。
- 定时发送心跳和资源指标。
- 接收模型下载、服务启停、日志查询等指令。
- 使用临时文件、校验和原子替换保证模型落位安全。
- 监控 Runtime 进程，按策略自动重启并上报状态。
- 断线后自动重连，支持局域网发现和固定地址连接。

## 6. 数据与状态

核心数据包括：节点、指标、模型、部署任务、服务和审计事件。

**指标分三层存储**，用同一张 `metric_rollups` 表的 `kind` 字段区分粒度：

| 层 | 粒度 | 默认保留 | 说明 |
|---|---|---|---|
| 原始 `raw` | 5 秒 | 2 天 | 实时曲线与排障 |
| 分钟级 `minute` | 60 秒 | 30 天 | 近一个月趋势 |
| 小时级 `hour` | 3600 秒 | 365 天 | 长期容量规划 |

维护由 `metric_rollup` 服务承担，每 60 分钟一轮，**顺序固定为「先聚合、后清理」**；
聚合失败则整轮不删。查询侧 `metrics_query.tier_plan()` 按窗口自动选层，
保证各层段落首尾相接、不重叠、不留缝。原始层 5 秒一条、每节点每天 1.7 万行，
保留一年是 630 万行 —— SQLite 扛不住，所以必须分层，而不是把保留期一味调长。

节点状态：`unknown`、`online`、`offline`。

Runtime 状态：`stopped`、`starting`、`running`、`error`。

部署状态：`pending`、`downloading`、`verifying`、`installing`、`ready`、`failed`。

所有控制指令带有 Task ID 或 Command ID，用于幂等、追踪和重试。

## 7. 关键设计纪律

1. 无法采集的数据保持为空，不以 0 代替。
2. 没有指标不等于节点离线，在线状态由心跳和超时规则判定。
3. 离线节点不继续展示旧的实时值。
4. IP 只用于连接，不作为设备身份。
5. 指令必须幂等，重复执行不能产生重复副作用。
6. 部署使用并发限制、磁盘检查、SHA-256 校验和原子替换。
7. 平台重启后先清除残留在线状态，再等待 Agent 重新注册。
8. Runtime 进程异常时记录原因，并按策略决定是否重启。

## 8. 当前实现与缺口

**已具备**（均有可复跑的验收脚本，见 `docs/acceptance/README.md`）：

- 局域网节点发现、注册、心跳、断线重连；
- 设备信息与指标采集（含来源标注的降级链），节点三态、服务七态、部署九态三套状态机；
- 模型库：流式上传、`Range` 断点续传、SHA-256 校验、量化精度 / 目标 SoC 等兼容性元数据与预检；
- 部署：并发队列、磁盘检查、逐秒进度、Self Test、失败重试、取消、原子替换；
- 服务托管：进程托管、资源准入、崩溃看门狗、日志拉取、平台侧主动探活、Agent 侧 auto_start 恢复；
- 网关：转发 + 计时 + 计数，OpenAI 兼容请求按原样透传；
- 设备文件管理：白名单沙箱内的浏览与双向传输，独立的单次传输令牌；
- 操作审计：所有写操作留痕，可按操作者 / 动作 / 时间查询。
- 指标分层保留：原始 2 天 / 分钟级 30 天 / 小时级 365 天，先聚合后清理、幂等可重跑，大屏回看上限 365 天；大屏与节点曲线按窗口自动选层；
- 备份与恢复：用 SQLite 一致性快照（`VACUUM INTO`）生成自包含备份包，而不是复制文件；支持只读校验、两步式恢复、恢复前自动另存当前数据；
- 部署失败回滚：落位前把旧文件移入回滚日志（同文件系统改名，零额外占用），失败则逐字节还原并验证；拿不到回滚点就不动手，Agent 崩溃后下一轮自动恢复。

**仍然欠缺的**：

| 缺口 | 性质 |
|---|---|
| ~~部署失败后的回滚~~ ✅ **已落地**（见 §8 已具备） | 已于 0.5.0-m5 完成 |
| 公网 P2P / Relay | 环境受限 —— 需要 STUN/TURN 或中继服务器，本机无法验证 |
| 内建 TLS | 设计取舍 —— 建议在反向代理后启用；Agent 已支持 `https://` → `wss://` |
| 用户与权限体系 | 设计取舍 —— 单团队局域网自用，用共享 token + 设备 token + 单次令牌分层 |
| 日志轮转、磁盘配额、多实例部署 | 生产化缺口，单机 SQLite 场景够用 |

> 「不打算做」的四项，理由逐条写在 `ROADMAP.md` 的「不打算做的事」一节 ——
> 那不是「还没做」，是环境上做不了或不该做。

## 9. 验收结论

当前版本（`0.5.0-m5`）已完成需求书 §1~§9 的全部条目，闭环为：

> 手机接入 → 节点监控 → 模型上传与下发 → 一键起服务 → 网关调用 → 查看请求量与延迟 → 文件管理 → 操作审计

唯一的例外是 **§9 的跨公网部分**：局域网内全链路已走通，公网部分需要 STUN/TURN 或中继服务器，
本机无法验证，因此明确不做。

验收数字见 `实现情况报告.md` 与 `CHANGELOG.md`。
